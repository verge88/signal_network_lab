# Версионируемые признаки и независимая проверка ML · 2.12

Движок 2.7 записывает `events-v1` во все новые прогоны процедур. Это отдельные счётчики и интегралы состояния, которые не зависят от ограничения трасс или подробного журнала. Существующие десять признаков `procedures-v2` / `messages-v1` сохранены в наборе `legacy-v1` для старых моделей.

## Порядок работы

1. Откройте **ML-детекторы**, выберите набор: сигнализация, пользовательские данные, ресурсы или все подсистемы.
2. Задайте 12–24 прогона. Включите **Три варианта связности**, если нужна проверка на новой топологии. Генератор создаёт исходную схему и варианты с одним и двумя дополнительными резервными каналами. Переименование и перемещение узлов не считаются новой топологией. Это ограниченное семейство схем, а не произвольное разнообразие сетей.
3. Нажмите **Сформировать**. Сохраняются конфигурации, seed, структурные отпечатки и типы воздействий каждого прогона. Чётные прогоны контрольные; нечётные содержат настроенные воздействия или автоматически выбранные surge / latency / node_down. Если задан только один тип воздействия, проверка на неизвестном типе требует другого датасета.
4. Выберите алгоритм и **Итоговую проверку**. «Независимые прогоны» разделяет run_id; «Новая топология» полностью исключает выбранный структурный отпечаток из train и validation; «Новый тип отказа» исключает все прогоны, содержащие выбранный тип. Укажите условие в **Только в test**.
5. Нажмите **Обучить модель**. Порог подбирается по validation, test в подборе не участвует. Если в частях не хватает нормальных или аномальных окон, обучение сообщает об этом и не подменяет выбранную схему случайным разбиением.
6. Смотрите обычные метрики, обнаруженные/пропущенные эпизоды, задержку и ложные тревоги/час. **Отчёт JSON** содержит исходный порог, состав частей, версию признаков и отдельные показатели для вручную изменённого порога.
7. Примените модель к другому сохранённому прогону. Для новых наборов нужен новый расчёт `events-v1`. Отсутствующие столбцы не заполняются нулями. Старые модели продолжают использовать свой исходный набор.

## Контракты

| Набор | Версия | Признаков |
|---|---|---:|
| Общие, совместимость | `legacy-v1` | 10 |
| Сигнализация | `signaling-v1` | 10 |
| Пользовательские данные | `userplane-v1` | 7 |
| Ресурсы | `resources-v1` | 13 |
| Все подсистемы | `combined-v1` | 30 |

Модель сохраняет точный порядок столбцов, набор и исходный контракт движка. Версия набора фиксирует определения ниже. Окна `[start,end)` имеют реальную длительность `window_seconds`, включая короткое последнее окно. События после конца эксперимента не добавляются в новые признаки предыдущих окон. Решение детектора доступно в конце окна.

### Сигнализация

| Столбец | Определение |
|---|---|
| `signal_arrivals_s` | Новые процедуры в секунду |
| `signal_completed_s` | Все фактически завершившиеся процедуры в секунду |
| `signal_failure_ratio` | Неуспешные / все завершившиеся процедуры |
| `signal_timeout_ratio` | Тайм-ауты / все завершившиеся процедуры |
| `signal_latency_p95` | p95 времени успешно завершившихся процедур, ms |
| `signal_retries_s` | Фактические повторы процедур / s |
| `transport_retries_s` | Повторы транспортных передач, включая управление / s |
| `control_messages_s` | Созданные управляющие сообщения / s |
| `control_reconnects_s` | Повторные начала установления ассоциации после первоначального / s |
| `neighbor_unavailable_ratio` | Средняя по времени доля недоступных записей о соседних узлах, направлениях каналов и ассоциациях в локальных представлениях |

### Пользовательские данные

| Столбец | Определение |
|---|---|
| `data_sent_s` | Созданные двусторонние пользовательские транзакции N3/N6 / s |
| `data_completed_s` | Завершённые транзакции, успешные и неуспешные / s |
| `data_loss_ratio` | Неуспешные / все завершённые транзакции |
| `data_rtt_p95` | RTT p95 успешных двусторонних транзакций N3/N6, ms |
| `data_goodput_mbps` | Полезные байты успешно завершённых транзакций × 8 / длительность окна / 10⁶ |
| `data_qos_violation_ratio` | Потерянные или превысившие бюджет QoS / все завершённые транзакции |
| `data_inflight_mean` | Среднее по времени число транзакций в работе |

Это показатели сервиса через совокупный путь N3/N6, а не отдельные счётчики физических пакетов каждого интерфейса. Полезные байты считаются один раз за успешную транзакцию, без повторов и служебных заголовков. Нулевые потери при нулевом количестве завершений не означают работоспособный сервис: проверяйте интенсивность и число пакетов в работе. Если пользовательский трафик выключен, показатели равны нулю.

### Ресурсы

| Столбец | Определение |
|---|---|
| `db_requests_s` | Обращения к ресурсному слою БД / s |
| `db_wait_mean_ms` | Среднее ожидание задач, начавших обслуживание либо завершившихся без старта, ms |
| `db_overflow_s` | Отказы из-за переполнения очереди / s |
| `db_timeouts_s` | Тайм-ауты БД / s |
| `db_queue_mean` | Средняя по времени суммарная очередь БД |
| `db_active_ratio` | Интеграл занятых соединений / суммарная настроенная ёмкость включённых узлов / длительность |
| `cache_hit_ratio` | Попадания в кэш данных или транзакций / обращения к ресурсному слою |
| `cache_occupancy_ratio` | Среднее заполнение всех конечных кэшей / их суммарная настроенная ёмкость |
| `cache_expired_s` | Удаления по TTL / s |
| `cache_evicted_s` | Вытеснения из-за ограниченной ёмкости / s |
| `context_occupancy_ratio` | Среднее заполнение хранилищ контекстов / их суммарная настроенная ёмкость |
| `context_expired_s` | Истечения контекстов / s |
| `context_rejected_s` | Отказы записи из-за лимита контекстов / s |

Очереди и занятость БД относятся к модели `queued`. Вероятностная модель не создаёт самостоятельной очереди. Ёмкости нормировки записываются в `telemetry.capacities`; это ёмкости всех настроенных хранилищ, включая неиспользуемые данным сценарием. Средние состояния — интегралы по времени, не снимки только на границе окна.

## Обнаружение и ложные тревоги

Расписание отказов и атак хранится отдельно от входов модели. Пересекающиеся интервалы одного прогона объединяются. Эпизод обнаружен, если конец аномального окна попал в интервал воздействия. Задержка — время первого такого решения минус начало воздействия. Короткое событие без решения внутри интервала может остаться пропущенным. Средняя задержка считается только для обнаруженных событий; пропущенные показаны отдельно.

Ложная тревога — начало серии соседних аномальных решений в полностью нормальном окне с нулевой меткой. Часовая частота = число таких начал × 3600 / наблюдавшиеся нормальные секунды. Окна с воздействием или положительной меткой исключены из нормальной экспозиции. При отсутствии экспозиции или метаданных показано «нет оценки», а не ноль. Короткие синтетические прогоны дают нестабильную часовую оценку.

`legacy-v1` содержит прежние показатели по окнам создания процедуры, которые могут учитывать исход после конца окна. Для оценки детектора, работающего в ходе эксперимента, используйте новые наборы со временем фактических событий.

## CSV и воспроизводимость

Экспорт датасета записывает списки типов отказов и интервалов как JSON внутри CSV. Для новых наборов обязательны `feature_set`, `feature_contract=procedures-v2`, `telemetry_contract=events-v1` и все выбранные столбцы. Нужны `run_id`, `label` и `time`. Для временных оценок добавьте `window_seconds` и `fault_intervals`; для независимых условий — `topology_id` и `fault_types`. Версии и контракты внутри одного файла смешивать нельзя. Старые CSV без версии используют `legacy-v1` / `messages-v1`.

Генератор даёт синтетические данные. Исключение топологии или отказа проверяет переносимость только внутри предоставленного семейства сценариев. Ни высокая F1, ни такие тесты сами по себе не подтверждают точность модели реального оборудования.
