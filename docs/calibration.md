# Калибровка 2.3

В **Эксперименты → Калибровка по измерениям** сохраните шаблон CSV и заполните измерениями своего изолированного стенда. «Настройки поиска» задают параметры, границы и бюджет; «Подобрать параметры» запускает фоновый расчёт с отменой. Отчёт экспортируется в JSON, подобранная конфигурация применяется с undo. Результаты хранятся в SQLite как записи `calibration`.

## Измерения

Одна строка — условие независимого опыта. Для нескольких условий одной записи используйте тот же `run_id`: группа целиком попадёт в train или test. Нельзя назначать независимые ID соседним окнам. Минимум четыре независимых ID, максимум 24 строки и 5 МБ. Топология и длительность берутся из проекта; измерения должны им соответствовать.

```csv
run_id,offered_rate,delivery_ratio,latency_mean,latency_p95,latency_p99,throughput,retry_ratio,recovery_ms,latency_samples_ms,scenario,incidents_json
```

Обязательны `run_id`, `offered_rate` и хотя бы одна измеренная метрика. Неизвестные значения оставляйте пустыми. Примеры и тесты используют синтетические данные; измерений оборудования в комплекте нет.

| Столбец | Определение |
|---|---|
| offered_rate | Суммарно новых процедур/с без повторов; доли потоков проекта сохраняются |
| delivery_ratio | Успешные процедуры / начатые, включая хвост |
| latency_mean/p95/p99 | Время успешной процедуры целиком, ms |
| throughput | Успешные завершения в `[0,duration)` / duration, без хвоста |
| retry_ratio | Повторы DATA / все попытки DATA транспорта; ACK исключены; управление и пользовательские пакеты включены |
| recovery_ms | Первое успешное завершение процедуры через затронутый объект после физического восстановления; среднее по событиям |
| latency_samples_ms | Необязательно: 20–20 000 задержек успешных процедур через вертикальную черту |
| scenario | Необязательная подпись условия; сама не изменяет конфигурацию |
| incidents_json | JSON-массив событий строки; пустое поле использует события проекта, `[]` отключает их |

JSON в CSV заключайте в кавычки с удвоением внутренних кавычек. Пример: `"[{""kind"":""link_down"",""target"":""ab"",""start"":2,""duration"":1}]"`. Объекты и время проверяются схемой проекта. Условия нагрузки и отказов включайте и в независимые проверочные опыты.

## Параметры и поиск

По умолчанию: четыре глобальных множителя latency/processing/loss/recovery с логарифмическим диапазоном 0.25–4, четыре прохода, до 40 вариантов, два seed на условие и 30% отложенных групп. Число проходов настраивается до 12, бюджет до 200, число seed до 5; максимум 16 параметров.

Кроме глобальных коэффициентов доступны абсолютные параметры узла или канала. Пути JSON: `global:latency`, `node:hss:capacity`, `link:ab:loss`. Узлы: обработка, БД, capacity, workers, вероятность ошибки/кэша, обнаружение, восстановление и задержки публикации. Каналы: задержка и потери обоих направлений, полоса, jitter, обнаружение/восстановление, heartbeat и таймер управления. Workers округляется до целого. Границы проверяются схемой. Глобальные коэффициенты применяются первыми, абсолютные значения — после них. Умножение не меняет исходный ноль потерь; выбирайте абсолютный `link:ID:loss`.

Координатный поиск проверяет соседние точки в линейной или логарифмической шкале; шаг уменьшается вдвое на каждом проходе. Повторные варианты кэшируются. Исходная конфигурация оценивается отдельно, даже если находится вне границ. Бюджет ограничивает варианты поиска, а не число запусков: каждый вариант выполняется по строкам train и seed; исходная и итоговая конфигурации дополнительно проверяются на test. Ограничение расчёта — оценочно 2 млн базовых процедур до учёта внутренних обменов.

## Независимая оценка

Группы перемешиваются воспроизводимо по seed проекта, минимум две остаются в каждой части. Seed симуляции выводится из seed проекта, SHA-256 run_id и номера повтора; варианты используют одинаковые seed. Для каждой строки предсказания усредняются по повторам, отдельные значения сохраняются.

Цель — взвешенное среднее квадратов нормированных MAE. Ошибки сначала усредняются внутри run_id, затем между группами: длинная запись не получает больший вес только из-за числа строк. Нормировка delivery_ratio равна 0.01, retry_ratio — `max(0.01, измерение)`, остальных — `max(1, измерение)`. Отсутствующее восстановление штрафуется длительностью опыта. Веса доступны через JSON `metric_weights`, по умолчанию равны 1.

Итоговые параметры фиксируются до первого вычисления test. Его метрики не используются для поиска; ухудшение не скрывается. Отчёт содержит исходную/подобранную конфигурации, границы, настройки, журнал поиска, число симуляций, ошибки, предсказания строк и диапазоны нагрузок train/test. 95% интервалы ошибки получаются из 1000 bootstrap-выборок отложенных групп. В нативной таблице показаны нормированные ошибки и интервалы test. Это интервалы средней ошибки предоставленных групп, а не границы точности оборудования.

Для массивов задержек вычисляются эмпирическое KS-расстояние и приближённое Wasserstein-расстояние по 1001 квантильной точке. Объединяются симуляционные выборки повторов; журнал — равномерный reservoir, точные агрегатные p95/p99 считаются по всем успешным процедурам. Статистическая значимость не заявляется.

Поиск не гарантирует глобальный оптимум; сочетания задержек и обработки могут быть неидентифицируемыми по агрегатам. Два отложенных run_id дают нестабильный интервал. Повторное ручное использование test для выбора границ превращает его в разработочную выборку. Для итогового вывода нужны новые независимые измерения, другие нагрузки, отказы и проверка распределений. Калибровка сама по себе не доказывает соответствие RFC или перенос на другую сеть.
