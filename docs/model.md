# Модель и методика исследования

## Модель и достоверность

В версии 2.2 добавлены **процедуры 5G SA** с вложенными вызовами NF, отдельными доменами NGAP/SBI/PFCP и контекстами регистрации/PDU. [Настройки, последовательности и границы 5G](5g.md). Для PFCP надёжный транспорт из описания ниже не применяется: датаграммы не имеют транспортных ACK/повторов, а RPC использует собственный таймер ответа.

По умолчанию работает **дискретно-событийная поведенческая модель процедур v2.3.0** (`engine=procedures`, определения признаков `procedures-v2`). Она не является протокольно совместимым операторским стендом. Соответствие RFC или точное воспроизведение оборудования не заявляется. [Ресурсы управления, распределённые представления и N3/N6 в 2.3](realism-2.3.md), [исправления 2.2.1](changes-2.2.1.md), [покрытие доработок 2.1](changes-2.1.md), [методика калибровки](calibration.md).

### Вычисляемая модель

- `rate` потока задаёт новые процедуры/с. Базовые поступления пуассоновские, события surge имеют точные границы. Периодический профиль: `1 + amplitude × sin(2πt/period)`; режим bursty дополнительно умножает интенсивность на 3 в первой пятой периода, иначе на 0.5 (среднее 1). Профиль аппроксимируется 100-ms сегментами. Абоненты равномерно выбираются из заданной группы. Размеры запросов/ответов постоянны либо логнормальны с заданным CV, ограничены 32–65536 B.
- Операции MAP UpdateLocation, SendAuthenticationInfo, Diameter ULR/AIR/CCR: запрос и соответствующий результат/ответ. ISUP: IAM → ACM и ANM, успех определяется ANM; вызов дальше не моделируется. Двухэтапная регистрация: AIR/AIA → ULR/ULA либо SendAuthenticationInfo/result → UpdateLocation/result. Следующий шаг начинается только после успешного ответа. На HLR/HSS/SCP хранятся состояния authenticated/registered; неподдерживаемый сервис или потеря состояния дают ответ об ошибке.
- Каждая процедура имеет session ID и transaction ID на этап. Для каждой попытки запланирован отдельный таймер; при равном времени таймер имеет приоритет перед ответом. Повторы сохраняют transaction ID этапа, кэш на адресате исключает повтор бизнес-операции; обработка и обратный ответ всё равно занимают ресурсы. Допустим поздний ответ на текущий этап во время паузы перед повтором. После перехода к следующему этапу старые ответы игнорируются. Пауза повторов экспоненциальная: `backoff × 2^attempt`.
- Узел имеет `workers` обработчиков и неперерываемую приоритетную очередь (0 — высший, FIFO внутри класса). `queue_limit` ограничивает ожидающих, отдельно от занятых обработчиков. `capacity` — общий предел начала обработок/с (минимальный интервал `1000/capacity`), `processing_ms` — время занятия одного обработчика. Это два независимых ограничения: предельная скорость примерно `min(capacity, workers×1000/mean_service_ms)`. Время постоянно, экспоненциально либо логнормально. На адресате HLR/HSS/SCP стоимость auth равна 1.5, прочих операций 2; для промаха кэша добавляется database_ms. Остальные роли выполняют пересылку с базовой стоимостью 1. Нет отдельного пула БД.
- Маршруты выбираются отдельно для запроса и ответа. PC определяет SS7-адресата; realm/host/application — Diameter-адресата. GTT выполняется после обработки запроса конкретным узлом, используя наиболее длинный префикс только его таблицы. До перевода следующий переход выбирается локальным правилом `GT:префикс → [ID]` (наиболее длинный префикс), затем `*`; без такого правила — среди соседних STP/SG. Непройденные, отключённые и несвязанные узлы не участвуют в переводе. Обходы уже пройденных узлов до перевода запрещены. После перевода действует маршрут к найденному PC; отсутствующий маршрут не заменяется правилом другого GTT-узла.
- Для разрешённого адреса таблица узла имеет вид `ключ → [ID следующих узлов]`, ключ — PC/realm или `*`. Заданные next hop упорядочены для резервирования; loadshare вращает предпочтения по абоненту. При отсутствии таблиц используется кратчайший путь; loadshare добавляет детерминированное распределение предпочтений. Учитываются Routing Context каналов M3UA, административные состояния ASP/peer и известная доступность. SS7 и M3UA принадлежат общему транспортному домену; Diameter — отдельному. Межпротокольного преобразования нет.
- Физический отказ действует на `[start,end)` отдельно от известной маршрутизаторам недоступности: `[start+detection+switch,end+recovery)`. Отказ короче detection не меняет опубликованное состояние. Канал может отказать только в одном направлении. При отказе узла его очередь и начатые обработки прерываются; занятость учитывается до отказа. node_restart также очищает кэш дубликатов и абонентское состояние. После восстановления допуск узла растёт от 10% до 100% за recovery_ramp_ms. По умолчанию у каждого узла отдельное представление доступности: соседи обнаруживают отказ и распространяют ROUTE_UPDATE через очереди и каналы, с версиями и периодическим обновлением. Время обнаружения можно задать для наблюдателя. Общее знание оставлено режимом сравнения; точные правила приведены в описании 2.3.
- Направления каналов независимы: сериализация `bytes×8/(Mbps×1000)` ms, буфер задан в байтах, обратные latency/loss могут отличаться. Сообщения фрагментируются по MTU и заголовкам. DATA и ACK расходуют полосу и буфер. ACK обрабатывается транспортом без очереди бизнес-узла. Задержка `max(0, Normal(latency×multiplier,jitter))`. События latency/loss используют максимальный множитель одного типа/объекта, в том числе 0. Независимые потери или марковские серии с заданной корреляцией: `P(loss|loss)=p+c(1-p)`, `P(loss|success)=p(1-c)`.
- Транспорт M3UA/Diameter: подтверждения фрагментов, ограниченное число повторов, SRTT/RTTVAR с коэффициентами 1/8 и 1/4, RTO `SRTT+4×RTTVAR` в заданных границах; после потери RTO удваивается. Повторные передачи не обновляют RTT. Упрощённое общее окно направления делится пополам при таймере и растёт примерно на `1/cwnd` при ACK. Получение всех фрагментов доставляет сообщение, даже если ACK потерян. Дубликаты фрагментов не доставляются повторно. Потоки обеспечивают упорядочивание сообщений внутри потока. Для SS7 транспортные повторы отключены; ACK — абстракция служебного трафика, не реализация MTP2.
- Исчерпание транспортного таймера завершает попытки отправителя, не отзывая уже доставленные данные и уже запланированные прибытия DATA. Неполная сборка прекращается, когда после остановки отправителя не осталось ожидаемых прибытий и всех фрагментов получить уже невозможно; тогда освобождается очередь потока. Это правило завершения передачи в симуляторе, а не полный автомат разрыва SCTP/TCP-ассоциации.
- `path_group` объединяет параллельные каналы между той же парой узлов с одинаковыми protocol/RC. При транспортном повторе после известного отказа основного пути выбирается доступный канал группы. Это приближение нескольких путей, без IP-адресов и полной SCTP multihoming state machine. В распределённом режиме промежуточный узел пересчитывает оставшуюся часть пути по своему знанию, с ограничением числа переходов; в общем режиме путь фиксирован при отправке. Состояние канала проверяется при окончании сериализации пакета, последующий отказ уже переданного пакета не отменяет прибытие.
- Измерение времени процедуры — от создания до успешного ответа последнего этапа. После окончания генерации обрабатывается хвост до исходов всех процедур. `delivery_ratio`, `loss_ratio`, latency и timeout_ratio относятся к когорте создания; latency учитывает только успехи. `throughput` — успешные завершения строго в `[0,duration)` / duration, хвост отдельными счётчиками. `completion_rate` — все исходы в физическом окне, `outstanding` — незавершённые на его правой границе. Очередь, повторы и смена маршрутов относятся к физическому окну события. `utilization` — максимальная занятость узла, делённая на workers и ширину окна. Поэтому показатели одного окна могут относиться к разным когортам; это указано в определениях.
- Журнал процедур — равномерный reservoir по всем исходам; журнал доставленных прикладных сообщений — отдельный reservoir. Лимит настраивается от 100 до 20000. Отдельный RNG выборки не влияет на физику; агрегаты используют все процедуры. В журналах и JSON доступны идентификаторы, этапы, маршруты, причины, повторы и затронутые события. Дополнительно: p99, статистика направлений и потоков, временная шкала состояний, время восстановления. `recovery` — первое успешное завершение на затронутом объекте после его физического восстановления; результат зависит и от интенсивности трафика.

Тайм-аут клиента не отзывает уже принятые в очередь и отправленные сообщения: они продолжают занимать транспорт и обработчики, сервер может сформировать поздний ответ. Такой ответ не возобновляет уже завершённую процедуру. Это учитывает остаточную нагрузку и наложение повторных запросов. Статистика повторов транспорта в отчёте включает последующий хвост после исхода процедуры.

Для направлений канала p95/p99 относятся к задержке успешно переданного пакета (DATA или ACK), включая ожидание сериализации, по равномерной выборке до 2000 пакетов на направление. Это отдельное определение, отличающееся от времени всей процедуры. Размер выборки записывается рядом. Для узлов p95/p99 считают ожидание и обработку сообщений до выхода из узла, включая поздние сообщения.

### Не реализовано

Двоичное кодирование, реальные сокеты, полные MTP2/3, SCCP/TCAP, MAP и ISUP автоматы, полного SCTP (TSN/SACK, fast retransmit, RFC congestion control и реальный multihoming), полных ASP/AS и Diameter peer/watchdog автоматов нет. CER/CEA, ASPUP/ASPAC и watchdog/heartbeat теперь имеют ресурсные сообщения и выбранные фазы; они не покрывают полный нормативный граф состояний, согласование возможностей или peer election. ROUTE_UPDATE — обобщённая модель распространения доступности, а не реализация операторского протокола маршрутизации. Нет полной семантики Result-Code/AVP, аутентификационной криптографии, мобильности и копии vendor overload policies. Измерений реального оборудования в комплекте нет.

Терминология и ориентиры: [RFC 4666 (M3UA)](https://www.rfc-editor.org/info/rfc4666/), [RFC 6733 (Diameter)](https://www.rfc-editor.org/info/rfc6733/), [RFC 9260 (SCTP)](https://www.rfc-editor.org/info/rfc9260/). Наличие их отдельных механизмов не означает соответствие стандартам. Для протокольной совместимости нужен изолированный стенд с настоящими стеками. [Калибровка CSV](calibration.md) сравнивает модель с измерениями на независимых опытах.

### Режим отдельных сообщений v1

`engine=messages` сохраняет прежнюю физику: один FIFO-сервер `max(1000/capacity,processing_ms)`, кратчайшие маршруты с мгновенным знанием отказов, независимая потеря целого сообщения, проверка тайм-аута только при следующем событии. Отправка одного сообщения считается успехом; адресные поля не влияют на маршруты, трасса — первые 1500 исходов, throughput включает хвост. Новые поля v2 в этом режиме не действуют; метка всегда scheduled. Этот режим нужен для воспроизведения прежних результатов, его ограничения намеренно сохранены. Версия признаков `messages-v1` несовместима с v2.

## Методика ML

Десять признаков: `rate`, `delivery_ratio`, `latency_mean`, `latency_p95`, `loss_ratio`, `timeout_ratio`, `queue_mean`, `queue_max`, `utilization`, `route_changes`. Seed, время, run_id и метка не входят в признаки.

В v2 хранятся три независимых флага: `scheduled_event` — окно пересекается с событием; `affected` — трафик обращался к затронутому объекту или был перенаправлен/отклонён из-за него; `observed_degradation` — в когорте создания есть хотя бы один неуспех или p95 выше `degradation_latency_ms` (по умолчанию 200 ms). Метку `label` выбирает `label_policy`; по умолчанию affected. Событие на неиспользуемом объекте не даёт affected. Эти признаки разметки не входят в ML-вектор. Воздействие не обязательно ухудшает сервис, а ухудшение возможно без запланированного события. Временные флаги воздействия и когортный флаг ухудшения имеют разные определения и не являются доказательством причинности.

Модели сохраняют `feature_contract`. Обучение на смеси v1/v2 и inference на несовместимом режиме отклоняются. Старые артефакты без этого поля считаются v1. При импорте внешней телеметрии явно добавляйте `feature_contract=procedures-v2`, если данные используют указанные выше определения; отсутствие столбца означает совместимость с прежней схемой v1.

Разбиение: независимые run_id случайно распределяются примерно 60/20/20. В validation и test минимум по два прогона. Доли округляются на уровне прогонов. Выбирается разбиение с обоими классами в каждой части; если такого разбиения нет, обучение отклоняется. Требуется минимум 6 независимых прогонов и достаточное разнообразие меток. Окна одного прогона не пересекаются между частями.

- Logistic Regression: StandardScaler, обученный только на train, `class_weight=balanced`.
- Random Forest: управляемое число деревьев, max_depth=10, min_samples_leaf=2, balanced.
- Isolation Forest: обучение только на нормальных окнах train. Score = `-score_samples`; больше означает более необычное окно. Порог подбирается по размеченным validation-данным. В режиме validation contamination задаёт внутренний offset модели и не изменяет используемый raw score. В режиме contamination порог равен `-offset_`, поэтому параметр определяет долю срабатываний на нормальном train. Оба режима доступны в интерфейсе и API.
- По умолчанию автоматический порог максимизирует F1 validation, затем однократно оценивается на test. Для IF доступен альтернативный порог по contamination. Порог можно задать и через API при обучении.
- Ручное изменение порога отображает test-метрики заново, не изменяя исходный отчёт модели. Это исследовательский просмотр: если порог выбирается по test, для честной итоговой оценки нужен новый независимый датасет.
- Важность: impurity importance для RF; абсолютные коэффициенты после стандартизации для LR. Это не причинные эффекты. Для IF важность не вычисляется.
- Разбиение по прогонам предотвращает утечку соседних окон, но не гарантирует перенос на другие топологии, новые виды событий и реальную сеть. Проверяйте такие сдвиги отдельными датасетами.

### CSV

UTF-8, запятая, заголовки:

```csv
run_id,label,time,rate,delivery_ratio,latency_mean,latency_p95,loss_ratio,timeout_ratio,queue_mean,queue_max,utilization,route_changes
experiment-001,0,0,80,0.999,23,32,0.001,0,0.3,2,0.4,0
```

`time` необязателен, остальные поля обязательны; label — 0 или 1, признаки — конечные числа. При импорте: максимум 20 000 строк и 10 МБ. Не назначайте разным окнам одного опыта разные run_id. Для реальной телеметрии используйте те же определения признаков и единицы измерения; для загрузки нужны минимум 30 строк, обучение отдельно проверяет run_id и состав классов.

## Серии и статистика

Множители применяются ко всем базовым интенсивностям потоков. На каждой точке используются `seed + repetition`, поэтому seed сопоставлены между группами. Выводится среднее и приближённый интервал `mean ± 1.96 × sample_std / sqrt(n)` для p95, delivery и throughput. При 2–5 повторениях нормальное приближение может быть неточным; для публикационных выводов увеличьте исследовательскую серию через API/несколько запусков и используйте подходящую статистическую методику. p95 в группе — среднее p95 отдельных прогонов, не объединённый p95 сообщений.
