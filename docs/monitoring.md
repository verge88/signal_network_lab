# Конструктор распределённого мониторинга

Окно **Исследование → Распределённый мониторинг…** позволяет собирать и сравнивать методы мониторинга на любой поддерживаемой топологии. Роли, зоны, формулы и группы признаков — параметры эксперимента. Фиксированного числа признаков, конкретного протокола или заранее заданного результата нет.

## Первый эксперимент

1. Создайте сеть и задайте обычные потоки. Для первого опыта удобен небольшой Diameter или SS7 проект с длительностью 30–60 секунд и небольшой нагрузкой.
2. Откройте конструктор. На вкладке **Участники и зоны** нажмите **Заполнить по топологии** или задайте назначения вручную. Автоматическое заполнение назначает узел с наибольшим числом каналов сборщиком; это только начальная конфигурация. Любой узел может быть сборщиком, участником и наблюдателем. У каждого участника одно назначение.
3. Укажите участника, сборщика, название зоны и независимого наблюдателя. Наблюдатель должен физически видеть нужный обмен. Он не получает глобальные счётчики симулятора. Если трафик обходит его, его счётчик останется нулевым.
4. На вкладке **Обмен** включите мониторинг. Настройте периоды опроса и решения, тайм-аут, TTL, глубину истории, размеры опроса/отчёта и приоритет. Приоритет 0 — высший. Через запятую перечислите разрешённые протоколы каналов. Синхронизация пересылает полученные отчёты другим сборщикам реальными сообщениями.
5. На вкладке **Признаки** изменяйте таблицу двойным щелчком. Каждая строка имеет уникальное латинское имя, числовую формулу и произвольную группу. Кнопка **Базовый набор** создаёт восемь примерных признаков трёх групп; это не воспроизведение конкретной научной методики.
6. Задайте физические воздействия обычным конструктором событий/атак либо добавьте синтетическое искажение отчётов. Поддерживаются масштабирование счётчика обработки, повтор прежних значений, отсутствие ответа и задержка отправки. Искажения не меняют фактические счётчики сети. Интервалы задаются в секундах; при перекрытии эффекты применяются в порядке строк.
7. Нажмите **Применить к проекту**, чтобы обычный F5 включал этот обмен. Профиль сохраняется вместе с проектом. Для отдельной исследовательской серии применять профиль к основному проекту необязательно.
8. На вкладке **Проверка метода** задайте 6–24 независимых прогона и нажмите **Сформировать датасет**. Чередуются контрольные прогоны без воздействий и прогоны со всеми заданными воздействиями. Интенсивность потоков меняется в пределах 0,85–1,15; seed каждого прогона сохранён. Для обучения требуется заданное воздействие, дающее оба класса в независимых частях.
9. Выберите RF, IF и/или логистическую регрессию. **Сравнить и выполнить абляцию** обучит полный вариант и варианты без каждой группы. Все они используют одинаковые исходные строки, seed и разделение целых run_id. После удаления группы модель обучается заново. Вариант без единственной имеющейся группы пропускается, потому что не оставляет входов.
10. Сравните F1, PR-AUC, FPR, обнаруженные эпизоды, задержку и ложные тревоги. На вкладке **Стоимость мониторинга** показаны служебные байты, тайм-ауты, число полученных отчётов и показатели сети каждого прогона. Результат может показать ухудшение или отсутствие пользы от выбранной архитектуры.

## Наблюдения и формулы

Формулы допускают числа, скобки, `+`, `-`, `*`, `/`, функции `abs`, `min`, `max`, `sqrt`, `log1p`, `safe_div(a,b)`. Последняя возвращает ноль при нулевом знаменателе. Ошибка области определения или деление на ноль обычным `/` останавливает расчёт с сообщением, а не подменяется подходящим значением. Число признаков — до 100. Произвольный Python, доступ к файлам, объектам и скрытым меткам отсутствует.

| Наблюдение | Определение |
|---|---|
| `reported_processed_s` | Сообщённая участником интенсивность завершённых обработок сигнальных сообщений; измеряется между полученными опросами |
| `reported_cpu_ms` | Сообщённое среднее время сообщения в узле: очередь + обработка, ms; несмотря на короткое имя это не чистое CPU-время |
| `reported_operation_entropy` | Энтропия Шеннона распределения операций в обработанных сообщениях, биты |
| `reported_peer_entropy` | Энтропия распределения адресатов/источников на участнике, биты |
| `reported_io_ratio` | Число обработанных сообщений с источником-участником / максимум(1, число сообщений с адресатом-участником) |
| `witness_messages_s` | Сообщения с исходным источником-участником, действительно обработанные независимым наблюдателем между решениями, /s |
| `report_missing` | 1, если нет принятого актуального отчёта; иначе 0 |
| `report_age_s` | Возраст измерения в принятом отчёте; при отсутствии актуального отчёта — настроенный TTL |
| `report_rtt_ms` | Время от отправки опроса до принятия отчёта сборщиком, включая очереди и обработку |
| `zone_median_processed_s` | Медиана актуальных принятых отчётов остальных участников той же зоны; сам участник исключён |
| `zone_mad_processed_s` | Медиана абсолютных отклонений этих значений от зональной медианы |
| `zone_coverage` | Доля остальных участников зоны, чьи актуальные отчёты доступны этому сборщику |
| `temporal_delta_processed_s` | Разность текущего сообщённого значения и значения на предыдущем решении; первое значение — 0 |
| `temporal_mean_processed_s` | Среднее предыдущих значений решений в ограниченной истории; до появления истории — 0 |

Пример зонального признака: `safe_div(abs(reported_processed_s-zone_median_processed_s),zone_mad_processed_s+1)`. Это выбор исследователя, не доказанная универсальная нормировка.

При отсутствии актуального отчёта сообщённые показатели равны нулю, но доступен явный флаг `report_missing`; возраст равен TTL. Время решения — конец окна. Временные признаки используют только прошлые решения. Зона использует только уже полученные отчёты; без синхронизации удалённые сведения могут отсутствовать. Отказавший сборщик не принимает решения. Просроченные ответы отбрасываются, уже записанные строки задним числом не изменяются. Скрытая физика и расписание воздействий используются исключительно для разметки и проверки.

## Схемы, обучение, импорт и экспорт

Контракт `monitoring-v1` хранит определения, порядок признаков, периоды, TTL и историю. SHA-256 схемы проверяется при импорте и применении. Изменение формулы или её смысла требует совместимого нового датасета и обучения; одинакового имени столбца недостаточно.

Датасеты и сравнения сохраняются в отдельной **Истории** конструктора. **Профиль JSON** переносит настройки, **Данные / отчёт** сохраняет полный JSON с версией и схемой, либо CSV датасета. Для импорта нужен JSON с исходной схемой и строками: одиночный CSV без схемы недостаточен. Допускаются внешние измерения с теми же определениями, `run_id`, `entity_id`, временем и бинарной меткой; происхождение обозначается `imported`, аппаратная точность автоматически не подтверждается. Максимум импортируемого JSON — 50 млн символов.

Таблицы сравнения, стоимости и первых 1000 наблюдений, а также график F1 экспортируются через обычное окно оформления. Полные строки доступны в JSON/CSV. Можно открыть другое сравнение и другой датасет, выделить модель и применить её: несовпадающие схемы отклоняются. Применение к обучающему датасету служит диагностике, а не новой независимой оценкой.

Разбиение выполняется по целым независимым прогонам, включая все узлы и окна прогона. Порог выбирается по validation. Строки одной сети в один период не считаются независимыми опытами. Метрики обнаружения рассчитываются отдельно по каждому участнику; ложные тревоги нормируются на суммарное нормальное время участников, поэтому единица — тревоги / узел·час.

## Границы модели

Это расширяемая поведенческая модель мониторинга. Сообщения проходят реальные для симулятора очереди CPU, транспорт, каналы, ACK и повторы. Используется кратчайший доступный маршрут по разрешённым типам каналов, фиксируемый на время одного сообщения. Это самостоятельный маршрут служебного слоя, не адресная маршрутизация прикладной операции. Циклы подключения и распространение доступности учитываются. При изменении состояния следующий опрос ищет маршрут заново.

Размер отчёта задаётся исследователем; список признаков не сериализуется автоматически в реальные 50 байт. Исследователь должен согласовать размер с выбранным кодированием. Заголовки, ACK, повторы и синхронизация добавляют нагрузку. Криптография, полноценные бинарные кодеки КЕ, синхронизация физических часов и стоимость вычисления ML-решения отдельным CPU-заданием здесь не моделируются.

Метка — пересечение окна с заданным воздействием на участника, прилегающий канал или поток с его участием; для отчётных искажений — с их расписанием. Это не определение состоявшегося перехвата, мошенничества или реальной компрометации. Обычные события сети могут дать те же наблюдения: обязательно включайте такие отрицательные примеры в исследование.

Сейчас доступны RF, IF и логистическая регрессия с бинарным решением. Многоклассовые решения, нейронные модели, каскады, автоматический поиск архитектуры и статистические интервалы разности абляций не реализованы. Окно не объявляет превосходство метода по одному F1. Выбор топологий, периодов, определений и независимая внешняя проверка остаются частью исследовательского плана. Параметры и результаты конкретной презентации не встроены.

До 100 000 опросов и решений за прогон, до 300 000 строк в серии; продолжают действовать общие ограничения сети и событий. Данные мониторинга входят в контрольные точки длительных прогонов. Снимки старого движка 2.10 нельзя продолжить в 2.11 из-за изменения состава состояния; проекты и сохранённые результаты остаются читаемыми.

Для независимой проверки новой связности включите **Три варианта связности** перед генерацией: к исходной сети добавляются один и два параллельных резервных канала. Это ограниченное семейство схем. Затем выберите **Новая топология** и укажите её структурный ID в поле **Только в test** либо оставьте автоматический выбор. Для произвольных новых сетей выполните отдельные эксперименты и импортируйте согласованный датасет с уникальными run_id. **Новый тип воздействия** требует разных типов в данных; нехватка классов даёт ошибку, без подмены независимой проверки случайным разбиением.
