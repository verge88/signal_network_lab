# Signal Lab

Локальная исследовательская лаборатория сигнальных сетей **SS7 / SIGTRAN / Diameter** с визуальным редактором топологии, дискретно-событийным симулятором, воспроизводимыми экспериментами и ML-детекторами.

## Запуск

Требуется Python 3.11+; проверено с Python 3.14, NumPy 2.3.5 и scikit-learn 1.8.0. Node.js и сборка фронтенда не требуются. В requirements-verified.txt зафиксированы прямые зависимости проверенной сборки; для строгого повторения сохраняйте также полный pip freeze своего окружения.

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe server.py
```

Открыть **http://127.0.0.1:8765**. Если зависимости уже установлены, достаточно `python server.py` или `./run.ps1`. Остановка — Ctrl+C в терминале сервера.

Приложение работает без внешних API, облачных аккаунтов, CDN и отправки исследовательских данных. Сервер слушает только loopback. В первом сеансе автоматически рассчитывается базовый прогон. Вычисление batch/ML блокирует другие вычислительные задания, но интерфейс и чтение истории остаются доступны.

## Возможности

- Редактор топологии: добавление, удаление, перетаскивание узлов; двусторонние связи; масштабирование; готовые SS7, Diameter и гибридная топологии.
- Узлы MSC/VLR, STP, SG, HLR/AuC, MME, DRA, HSS, SCP; производительность, обработка, FIFO-очередь, состояние, point code / realm как метаданные.
- Каналы: задержка, джиттер, полоса, вероятность потерь и административное включение.
- Сигнальные потоки: источник, назначение, протокольный домен, метка операции, msg/s, размер сообщения, тайм-аут.
- События по времени: отказ узла/канала, изменение интенсивности, задержки и потерь; дробные границы времени поддерживаются.
- Метрики доставки, p95, средней задержки, пропускной способности, очередей, загрузки узлов; выборка трасс сообщений.
- Серии с множителями нагрузки и повторениями по seed; сравнение прогонов; оценки разброса среднего.
- ML: Random Forest, Logistic Regression, Isolation Forest; генерация размеченной телеметрии; CSV-импорт; разделение по run_id; validation-порог; test-метрики, матрица ошибок, важность признаков, изменение порога, применение сохранённого детектора к прогону.
- SQLite-история проектов, датасетов, моделей и серий; JSON/CSV-экспорт; восстановление конфигурации прогона.

## Быстрый исследовательский сценарий

1. В **Топологии** выберите Hybrid core и запустите базовый эксперимент. Нажмите на STP Alpha, настройте capacity / queue_limit. Каналы выбираются нажатием на линию.
2. В **Экспериментах** запланируйте отказ `stp-a` на интервале 20–40 s. Запустите прогон, сравните его с базовым в **Результатах**. Изучите смену маршрутов и потери сообщений в пути.
3. Снизьте производительность HLR или повысьте интенсивность потоков. Запустите серию `0.5, 1, 1.5, 2` с тремя повторениями и сравните p95/доставку.
4. В **ML-детекторах** сформируйте датасет из 12 прогонов. Половина прогонов содержит нормальный фон, половина — события текущего сценария. Если сценарий пуст, генератор чередует всплеск, рост задержки и отказ конечного узла.
5. Обучите Random Forest, затем Logistic Regression и Isolation Forest. Выберите модели из библиотеки для сравнения качества. Проверьте модель на отдельном новом прогоне.
6. Экспортируйте датасет и полный JSON эксперимента для повторения исследования.

## Модель и достоверность

Это **исследовательская модель на уровне сообщений и транспортных доменов**, не протокольно совместимый операторский стенд. Соответствие RFC или точное воспроизведение оборудования не заявляется. Наличие значка STP/HSS не означает реализацию функций соответствующего сетевого элемента.

### Вычисляемая модель

- Сообщения поступают по кусочно-однородному пуассоновскому процессу; события нагрузки изменяют интенсивность на точных временных границах.
- Узел — один FIFO-сервер. Время обслуживания, ms: `max(1000 / capacity, processing_ms)`. `queue_limit` ограничивает ожидающие сообщения; одно сообщение может обслуживаться отдельно от очереди. При переполнении сообщение отбрасывается.
- Маршрут — путь с минимальной суммой задержек каналов и обработки промежуточных/конечных узлов, выбираемый при отправке. Учитываются административные состояния и действующие отказы. SS7/M3UA совместимы в одном абстрактном домене; Diameter использует свои каналы. Межпротокольного преобразования нет.
- Пакетное обслуживание на канале: `bytes × 8 / bandwidth`; каналы full duplex, направления сериализуются независимо. Задержка выбирается из `max(0, Normal(latency × multiplier, jitter))`. Потери независимы для каждого сообщения на каждом переходе.
- События действуют на `[start, start + duration)`. При наложении событий одного типа/объекта используется максимальный множитель. 0 допустим; множитель потерь действует на базовую вероятность (если базовая потеря 0, результат остаётся 0).
- При отказе маршрут пересчитывается для новых сообщений. Сообщения в пути не перемаршрутизируются. Доступность узла проверяется при поступлении; начатая обработка не прерывается отказом. Состояние канала проверяется при передаче после обработки; изменение состояния уже летящего сообщения не отменяет его прибытие.
- Узел-источник и узел-назначение тоже выполняют обработку. Время измеряется от создания до завершения обработки назначения. Тайм-аут проверяется на границах событий; для записи timeout наблюдаемая задержка может превышать значение тайм-аута.
- После окончания генерации обрабатывается хвост очередей. Задержки считаются только для доставленных сообщений. Delivery/loss/latency/queue агрегируются по окну **создания** сообщения, а не окну его завершения. `utilization` — максимальная занятость отдельного узла в физическом временном окне, в диапазоне 0–1. `route_changes` считает изменения выбранного пути последовательных сообщений одного потока.
- Трасса ограничена первыми 1500 завершившимися сообщениями, в интерфейсе показываются первые 150 подходящих записей этой выборки. Все сообщения учитываются в агрегатах. При высокой задержке выборка трасс имеет смещение к ранним завершениям.

### Не реализовано

Двоичное кодирование и реальные сокеты SS7/SCTP/Diameter, MTP2/3, SCTP multihoming/streams/retransmission/congestion control, ASP/AS state machine, SCCP/GTT, TCAP-диалоги, MAP/ISUP-процедуры, Diameter capabilities/watchdog/realm routing, транзакционные request/answer, повторные передачи и производственные таймеры. MAP/ISUP/Diameter-операции служат метками; point code и realm — описательные поля. Конфигурация этих полей не меняет выбор пути.

В основе терминологии профилей: [RFC 4666 (M3UA)](https://www.rfc-editor.org/rfc/rfc4666) и [RFC 6733 (Diameter)](https://www.rfc-editor.org/rfc/rfc6733). Для исследований протокольной совместимости нужен отдельный изолированный стенд с настоящими реализациями стека и калибровкой на измеренной телеметрии. CSV-импорт позволяет обучать детекторы на внешней телеметрии, но не калибрует симулятор автоматически.

## Методика ML

Десять признаков: `rate`, `delivery_ratio`, `latency_mean`, `latency_p95`, `loss_ratio`, `timeout_ratio`, `queue_mean`, `queue_max`, `utilization`, `route_changes`. Seed, время, run_id и метка не входят в признаки.

Метка синтетических данных: **1, если окно пересекается хотя бы с одним запланированным событием**. Даже событие на неиспользуемом канале даст метку 1 — это ground truth сценария, а не гарантия наблюдаемой неисправности. Окна с обычными случайными потерями без события получают 0. Это ограничение важно для интерпретации F1.

Разбиение: независимые run_id случайно распределяются примерно 60/20/20. В validation и test минимум по два прогона. Доли округляются на уровне прогонов. Выбирается разбиение с обоими классами в каждой части; если такого разбиения нет, обучение отклоняется. Требуется минимум 6 независимых прогонов и достаточное разнообразие меток. Окна одного прогона не пересекаются между частями.

- Logistic Regression: StandardScaler, обученный только на train, `class_weight=balanced`.
- Random Forest: управляемое число деревьев, max_depth=10, min_samples_leaf=2, balanced.
- Isolation Forest: обучение только на нормальных окнах train. Score = `-score_samples`; больше означает более необычное окно. Порог подбирается по размеченным validation-данным. В режиме validation contamination задаёт внутренний offset модели и не изменяет используемый raw score. В режиме contamination порог равен `-offset_`, поэтому параметр определяет долю срабатываний на нормальном train. Оба режима доступны в интерфейсе и API.
- По умолчанию автоматический порог максимизирует F1 validation, затем однократно оценивается на test. Для IF доступен альтернативный порог по contamination. Порог можно задать и через API при обучении.
- Ручное изменение порога отображает test-метрики заново, не изменяя исходный отчёт модели. Это исследовательский просмотр: если порог выбирается по test, для честной итоговой оценки нужен новый независимый датасет.
- Важность: impurity importance для RF; абсолютные коэффициенты после стандартизации для LR. Это не причинные эффекты. Для IF важность не вычисляется.
- Разбиение по прогонам предотвращает утечку соседних окон, но не гарантирует перенос на другие топологии, новые виды событий и реальную сеть. Проверяйте такие сдвиги отдельными датасетами.

### CSV

UTF-8, запятая, заголовки:

```csv
run_id,label,time,rate,delivery_ratio,latency_mean,latency_p95,loss_ratio,timeout_ratio,queue_mean,queue_max,utilization,route_changes
experiment-001,0,0,80,0.999,23,32,0.001,0,0.3,2,0.4,0
```

`time` необязателен, остальные поля обязательны; label — 0 или 1, признаки — конечные числа. При импорте: максимум 20 000 строк и 10 МБ. Не назначайте разным окнам одного опыта разные run_id. Для реальной телеметрии используйте те же определения признаков и единицы измерения; для загрузки нужны минимум 30 строк, обучение отдельно проверяет run_id и состав классов.

## Серии и статистика

Множители применяются ко всем базовым интенсивностям потоков. На каждой точке используются `seed + repetition`, поэтому seed сопоставлены между группами. Выводится среднее и приближённый интервал `mean ± 1.96 × sample_std / sqrt(n)` для p95, delivery и throughput. При 2–5 повторениях нормальное приближение может быть неточным; для публикационных выводов увеличьте исследовательскую серию через API/несколько запусков и используйте подходящую статистическую методику. p95 в группе — среднее p95 отдельных прогонов, не объединённый p95 сообщений.

## Данные и API

```text
server.py              FastAPI, валидация запросов, экспорт, локальный сервер
lab/schema.py          Модели узлов, каналов, потоков, событий и проекта
lab/simulator.py       Дискретно-событийный симулятор
lab/ml.py              Обучение, разбиение, метрики, сохранение и inference
lab/storage.py         SQLite, изолированные соединения, WAL
static/                Интерфейс без сборки и внешних зависимостей
tests/test_lab.py      Тесты симуляции и интеграционного workflow
data/lab.sqlite3       История и датасеты (создаётся автоматически)
data/models/*.joblib   Внутренние артефакты моделей
```

Swagger: **http://127.0.0.1:8765/api/docs**. Основные endpoints: `/api/presets/{name}`, `/api/validate`, `/api/projects`, `/api/simulate`, `/api/sweep`, `/api/datasets/generate`, `/api/datasets/import`, `/api/train`, `/api/predict`, `/api/models/{id}/evaluate`, `/api/records/{kind}`, `/api/export/{kind}/{id}`.

Проверяется структура проекта и ссылки на объекты. Лимиты: 60 узлов, 150 каналов, 30 потоков, 30 событий, 600 s; оценочный верхний предел одного прогона 350 000 сообщений, генератора 1,5 млн базовых сообщений, серии 1 млн. Пуассоновское число сообщений не является жёсткой границей; генератор учитывает базовые потоки для совокупного лимита, а индивидуальная валидация — максимальный множитель всплеска.

История в интерфейсе ограничена последними 100 записями каждого типа. Данные можно резервировать копированием `data` при остановленном сервере. Проекты/прогоны экспортируются в JSON; веса моделей не публикуются в JSON. Внешние pickle/joblib не импортируются. Сервер отклоняет посторонний Host и browser Origin; он предназначен для одного локального исследователя, без многопользовательской аутентификации. Не выставляйте его напрямую в интернет.

## Проверка

```powershell
python -m pip install -r requirements-dev.txt
python -m unittest discover -s tests -v
node --check static/app.js
```

Node нужен только для необязательной проверки синтаксиса JS. Тесты используют временную SQLite и временные модели, не меняя исследовательскую историю. Они проверяют детерминизм, сохранение числа сообщений, транспортные домены, полный loss, тайм-аут, переполнение, утилизацию, резервный маршрут, временные границы событий, параллельную инициализацию БД, валидацию и полный ML/CSV/batch workflow.
